# 계획 1: 엔진 기반과 결과 일치 검증 도구 — 구현 계획 (한국어판)

> 원본: `2026-11-04-plan1-engine-foundation.md`. 구현자는 영문판을 따르며, 두 문서는 함께 갱신합니다.
> 코드 이름, 명령, 파일 경로는 영문판과 같게 두었습니다.

**목표:** 기본 요소, 세이브 형식, 데이터 로딩이 C# 기준과 정확히 같은 결과를 내는 Rust 작업 공간을 만듭니다.
같은지는 C#에서 뽑은 대조 자료로 확인합니다. 이후 계획들이 시스템을 하나씩 더해 갈 CI와 대조 도구도 함께 만듭니다.

**구조:** C#이 계속 기준입니다. Unity의 명시적 EditMode 테스트 하나가 대조 자료(기본 연산 값, 데이터 덤프와
해시, 턴별 섹션 해시, 표본 턴의 시스템별 스냅숏)를 `engine/fixtures/`로 내보냅니다. Rust 크레이트는 각
부분을 재현하고, 테스트가 그 파일들과 비교합니다. `fes-parity` 프로그램은 처음 어긋난 곳을 알려 줍니다.

**기술:** 고정된 Rust stable(`rust-toolchain.toml`), cargo 워크스페이스, `serde`/`serde_json`(테스트와 대조 전용),
`flate2`, `sha2`. 내보내기는 Unity 6000.6.6f1 EditMode 테스트(C#). GitHub Actions.

**설계서:** 6, 7.1, 7.4장. 로드맵: `2026-11-04-rust-port-roadmap.ko.md`.

## 전체 제약

- 시뮬레이션 코드는 정수와 `Fx`(`i64` 안의 Q47.16)만 씀. `fes-core`, `fes-data`, `fes-save`에서
  `clippy::float_arithmetic` 금지.
- 반올림은 `Fx.RoundShift` / `Fx.MulInt`와 똑같이 0에서 먼 쪽으로.
- 문자열 해시는 UTF-8 바이트가 아니라 UTF-16 단위로(`DetHash.Of`가 C# `char`를 돌기 때문).
- 바이너리 형식은 .NET `BinaryWriter`: 리틀 엔디언 정수, 문자열은 7비트 인코딩 길이 + UTF-8.
- 세이브: 매직 `0x53454646`, `FormatVersion = 1`.
- 저장 구성요소는 키의 서수 비교 순서로 정렬.
- 코드 한도(DEC-108): 인지 복잡도 15, 함수 80줄, 매개변수 7, 파일 1,000줄, 중첩 3. `rustfmt`와
  `clippy -D warnings` 통과.
- 규칙, 수치, 연산 순서는 그대로 옮김. 도중에 찾은 C# 버그는 고치지 않고 `docs/superpowers/port-notes.md`에 기록.
- 코드, 주석, 커밋은 영어.

## 검토 중점 (테스트가 놓치기 쉬운 입력)

- 비ASCII 문자열(악센트 이름, BOM)이 C#과 같은 해시를 내는지 — 작업 3에 `"Ærø"`, BOM, UTF-16 두 단위짜리 `"𝔄"` 포함.
- 빠른 경로를 벗어난 `Fx`(2^31 초과, `i64::MAX >> 16` 근처)가 C#의 `decimal` 경로와 같은지 — 작업 2에 포함.
- CRLF, 쉼표·줄바꿈·`""`가 든 따옴표 필드, `#` 주석, 빈 줄, 짧은 행 — 작업 5.
- 잘리거나 엉뚱한 파일을 `read_save`에 넣으면 패닉 없이 오류 — 작업 4.
- `config.csv`에 없는 키는 코드 기본값, 모르는 키는 오류 — 작업 6.

### 작업 0: 기준 시점 고정
1. 다른 세션의 작업이 커밋됐는지 확인(`git status --short Assets/_Game`에 수정된 시뮬레이션 파일 없음). 남아 있으면 멈추고 사용자에게 물음.
2. 그 커밋에서 EditMode 테스트 전체 실행. `GoldenRunTests` 포함 모두 통과해야 함.
3. 커밋 해시를 설계서 6장(영문·한국어)과 결정 기록(DEC)에 기록: "Rust 이식의 C# 기준은 `<해시>`, 이 시점부터 C# 시뮬레이션 코드 고정." 설계서 7.3의 웹 턴 출발점을 `00_Architecture.md`의 낡은 수치 대신 기록.
4. 메인 체크아웃에서 `rust-port` 브랜치 생성(작업 1의 내보내기에 Unity 에디터가 이 프로젝트를 열어야 하므로 워크트리 없음).
5. 문서들과 설계서·계획서·대회 규칙 정리 파일을 커밋.

### 작업 1: C# 대조 자료 내보내기
- `ParityFixtureExporter.WritesParityFixtures`(명시적 테스트)가 남길 골든 런 4개(`Default_Seed1_ThirtyYears`, `Default_Seed2`, `Default_Seed3`, `NoBills`)를 만들고 다음을 씀:
  - `primitives.json`: `Fx` 연산, `DetHash`, `DetRandom` 값 목록(경계값 포함, 연산마다 300개).
  - `data/`: 설정 실제값과 기본값, 설정 필드 전체, 정의·지도 덤프, 해시(content, map, data, config).
  - `runs/<이름>/start.save`(생성 직후 세이브), `turns.json`(턴마다 세계 해시와 섹션별 해시, 최종 SHA가 `GoldenRunTests` 값과 같은지 검사).
  - 30년 런의 표본 턴(0, 1, 3, 51, 52, 53, 103, 104)에서 시스템 하나와 단계별 이벤트 처리가 끝날 때마다 바뀐 섹션.
- 시뮬레이션 코드는 건드리지 않음. 턴 진행을 공개 멤버로 재현하고, 그 결과가 `AdvanceTurn`과 같은지 확인. 공개되지 않은 멤버가 필요하면 C#을 고치지 않고 멈춰서 보고.
- 실행 후 `GoldenRunTests` 재확인. 50 MB를 넘으면 Git LFS 사용.

### 작업 2: 작업 공간, CI, `Fx`
- 워크스페이스(`fes-core`, `fes-save`, `fes-data`, `fes-parity`), 툴체인 고정, clippy·rustfmt 설정, 파일 길이 검사 스크립트, GitHub Actions(포맷, clippy, 테스트, 대조 도구 실행).
- 대조 자료의 모든 `Fx` 연산 값과 같아지도록 `Fx` 구현. C# `decimal` 경로는 `i128`로 계산. 어긋나면 그 경로만 `decimal` 반올림을 흉내 내고 기록.

### 작업 3: `DetHash`와 `DetRandom`
- 해시 함수와 난수 뽑기 순서가 대조 자료와 같아야 함. `of`는 UTF-16 단위로 돌림.

### 작업 4: .NET 바이너리 입출력과 세이브 형식
- `start.save`를 읽고 다시 쓰면 바이트가 똑같아야 함. 세계 해시가 C#의 0턴 값과 같아야 함. 헤더의 데이터 해시·시드·턴이 맞아야 함.
- 문자열 길이 접두사(200바이트 → `[0xC8, 0x01]`) 확인.
- 매직이 틀리거나, 버전이 다르거나, 길이가 끝을 넘거나, 파일이 잘리면 패닉 없이 오류.

### 작업 5: CSV 읽기
- C# `CsvTable` 테스트를 그대로 옮기고, CRLF·따옴표·주석·빈 줄·짧은 행이 섞인 입력, 닫히지 않은 따옴표, 숫자로 된 enum 이름 거부를 추가.

### 작업 6: `SimulationConfig`
- 설정 실제값, 필드 전체, 해시가 C#과 같아야 함. 빈 설정은 C#의 코드 기본값과 같아야 함. 모르는 키는 그 키 이름을 담은 오류.
- C#의 `Apply*` 주제별로 파일을 나눠 각 1,000줄 이하.

### 작업 7: 정의, 지도, 데이터 해시
- 정의·지도 덤프와 content/map/data 해시가 C#과 같아야 함. CRLF와 BOM은 해시를 바꾸지 않음. 파일 읽는 순서도 C#과 같음.

### 작업 8: 대조 도구
- `fes-parity --fixtures <폴더>`가 데이터 해시와 `start.save` 왕복을 확인하고, 섹션마다 `같음`, `다름`(처음 다른 바이트 위치), `미이식`을 보여 줌. 다른 섹션이 없으면 성공.
- 이식한 섹션 목록은 이번 계획에서는 비어 있고, 계획 2부터 채움.
- **push는 사용자에게 먼저 물어봄.** 허락하면 push 후 CI 통과 확인, 아니면 같은 명령을 로컬에서 실행.

각 작업은 테스트를 먼저 쓰고(실패 확인) → 구현 → 통과 확인 → 커밋 순서로 진행합니다.
